# MII IG Publisher Migration

Comprehensive knowledge for migrating MII Kerndatensatz modules from Simplifier-based Implementation Guides to the HL7 FHIR IG Publisher with multi-language support.

**Version**: 1.0.0

## When to Use This Skill

- Migrating a module from Simplifier IG to IG Publisher
- Setting up multi-language IG support (EN/DE)
- Creating `.github/workflows/ig-publisher.yml` for CI/CD
- Translating Simplifier `.page.md` files to IG Publisher `input/pagecontent/` pages
- Replacing Simplifier-specific tags (FQL, render, tree, tabs, pagelink)
- Setting up GitHub Pages deployment for IG builds

## Critical Rules

### Encoding

**ALWAYS use real UTF-8 characters in all files:**
- German: ä ö ü Ä Ö Ü ß — NEVER ae oe ue Ae Oe Ue ss
- The IG Publisher, SUSHI, Git, and all modern tools handle UTF-8 natively
- There is NO encoding safety benefit from ASCII transliteration
- This applies to ALL files: pagecontent, translations, intro-notes, FSH

### Language Strategy

The MII standard follows the `kerndatensatz-basis` pattern:
- **English = primary language** (`i18n-default-lang: en`)
- **German = translation** (`i18n-lang: [de]`)
- Primary content in `input/pagecontent/*.md` (English)
- German translations in `input/translations/de/pagecontent/*.md`
- Menu/UI translations via PO files in `input/translations/de/`

## Infrastructure Setup

### 1. ig.ini

```ini
[IG]
ig = fsh-generated/resources/ImplementationGuide-{id}.json
template = fhir2.base.template#current
usage-stats-opt-out = true
```

**Important**: Use `fhir2.base.template#current` (not `fhir.base.template`) — the `fhir2` template includes built-in multi-language support with language switcher.

### 2. sushi-config.yaml Additions

Add these sections to existing sushi-config.yaml:

```yaml
# Pages section — list all pagecontent files with hierarchy
pages:
  index.md:
    title: Home
  # ... add sub-pages with indentation for hierarchy

# Menu with English labels
menu:
  Home: index.html
  # ... menu structure
  Artifacts: artifacts.html
  Downloads: downloads.html

# i18n and IG Publisher parameters
parameters:
  i18n-default-lang: en
  i18n-lang:
    - de
  translation-sources:
    - input/translations/de
  path-pages:
    - input/intro-notes
  excludettl: true
```

### 3. Directory Structure

```
input/
├── pagecontent/              ← English pages (primary)
│   ├── index.md
│   ├── module-description.md
│   └── ...
├── translations/de/
│   ├── pagecontent/          ← German pages (mirror English filenames)
│   │   ├── index.md
│   │   ├── module-description.md
│   │   └── ...
│   ├── intro-notes/          ← German profile intro notes
│   └── ImplementationGuide-{id}.po  ← Menu/UI translations (PO format)
├── intro-notes/              ← English profile intro notes
│   └── StructureDefinition-{id}-intro.md
├── images/                   ← Images (lowercase directory name!)
└── includes/                 ← Optional HTML fragments (headers, etc.)
```

### 4. GitHub Actions Workflow

The `ig-publisher.yml` workflow uses:
- Docker image: `ghcr.io/gefyra/ig-publisher-with-snapshot-support:latest`
- NGINX proxy for CDS terminology server (mTLS with GitHub secrets)
- Steps: Checkout → Graphviz → NGINX → SUSHI → IG Publisher → GitHub Pages

Required GitHub secrets (shared across all MII modules):
- `CDS_DEV_CLIENT_CERT`
- `CDS_DEV_CLIENT_KEY`
- `CDS_DEV_CLIENT_CERT_PASSWORD`

GitHub Pages deployment pattern:
- `main`/`master` branch → published to root (`https://{owner}.github.io/{repo}/`)
- Feature branches → published to subdirectories (`https://{owner}.github.io/{repo}/{branch}/`)

Reference implementation: `kerndatensatz-basis/.github/workflows/ig-publisher.yml`

## Simplifier Tag Replacement Reference

### Tags That Are Completely Removed

| Simplifier Tag | Reason |
|---|---|
| `{{page-title}}` | IG Publisher generates page titles from `sushi-config.yaml` `pages:` section |
| `{{index:current}}` / `{{index:root}}` | IG Publisher auto-generates `toc.html` |
| `<tabs>...</tabs>` | IG Publisher has built-in Differential/Snapshot/XML/JSON/TTL tabs on profile pages |
| `{{tree, buttons}}` / `{{tree:X}}` on profile pages | Auto-generated by IG Publisher |
| `{{xml}}` / `{{xml:X}}` | Auto-generated XML view on every resource page |
| `{{json}}` on profile pages | Auto-generated JSON view on every resource page |
| `{{link}}` | IG Publisher shows canonical URL automatically |

### Tags That Are Replaced

| Simplifier Tag | IG Publisher Equivalent |
|---|---|
| `{{pagelink:SomeTopic}}` | `[Link Text](some-topic.html)` |
| `{{pagelink:SomeTopic, text:Custom}}` | `[Custom](some-topic.html)` |
| `{{render:path/to/image.png}}` | `![Alt Text](image-filename.png)` (images in `input/images/`) |
| `{{render:https://canonical-url}}` (resource) | `[Resource Name](ResourceType-id.html)` |
| `{{json:instance-id}}` (example embed) | `See [Example Name](ResourceType-instance-id.html)` |
| `{{tree:canonical-url}}` on content pages | `See [Profile Definition](StructureDefinition-id.html)` |
| `{{table:canonical-url}}` | Link to auto-generated page or static Markdown table |
| `<fql>...</fql>` | Remove entirely (auto-generated) or replace with static Markdown table |
| `<img src="https://raw.githubusercontent.com/...">` | `![Alt](filename.png)` |
| `<iframe src="...">` | Remove (note: "Preview available via SDC Form Renderer") |
| `## {{page-title}}` | Remove heading entirely (IG Publisher generates it) |
| `{{page:FQL-Beschreibung}}` (include) | Content goes into `input/intro-notes/StructureDefinition-{id}-intro.md` |

### FQL Patterns That Become Auto-Generated

These FQL patterns produce content that IG Publisher generates automatically on profile pages:

| FQL Pattern | Auto-Generated By |
|---|---|
| Profile metadata table (url, status, version, baseDefinition) | Profile page header |
| `StructureDefinition.description` inline | Profile page description |
| Must-Support elements table | Differential view with S-flag |
| Constraints/invariants table | Constraints section |
| Terminology bindings table | Bindings section |
| CapabilityStatement interactions/search/operations | CapabilityStatement page |

### Content That Moves to intro-notes

Simplifier profile pages (`Observation.page.md`, etc.) often contain custom content mixed with dynamic FQL/tabs. In IG Publisher:

- Custom descriptions, hints, mapping tables → `input/intro-notes/StructureDefinition-{id}-intro.md`
- Notes appended after profile → `input/intro-notes/StructureDefinition-{id}-notes.md`
- Everything auto-generated (tree, constraints, bindings, XML/JSON) → removed from custom content

## Page Migration Workflow

For each Simplifier `.page.md` file:

1. **Read** the original German Simplifier source
2. **Strip** all Simplifier-specific tags using the replacement table above
3. **Write English translation** → `input/pagecontent/{name}.md`
   - Professional technical English
   - Keep FHIR terms, instrument names, code examples, URLs unchanged
   - Do NOT add a title heading (IG Publisher generates from config)
4. **Write cleaned German version** → `input/translations/de/pagecontent/{name}.md`
   - Same structure as English (tags stripped, links mapped)
   - Keep original German text with proper UTF-8 umlauts
   - Do NOT transliterate umlauts to ASCII

### File Naming Convention

Simplifier topic names → IG Publisher filenames:
- Use lowercase kebab-case: `BeschreibungModul.page.md` → `module-description.md`
- Use English names for filenames
- Keep names short and descriptive
- Match filenames between English and German directories exactly

## Verification Checklist

After migration:
1. `sushi .` — compiles with 0 errors
2. IG Publisher build produces `output/` directory
3. GitHub Pages accessible with language switcher (EN/DE)
4. All profile pages show intro-notes content
5. All cross-references between pages resolve
6. Images render correctly
7. No Simplifier tags remain in output files: `grep -r '{{' input/pagecontent/`
8. German files use real umlauts: `grep -P '[^a-z]ae[^a-z]|[^a-z]oe[^a-z]|[^a-z]ue[^a-z]' input/translations/de/pagecontent/` should return minimal results (only legitimate English words)
